# Paper ↔ Tailwind v4: Coverage Gaps and Sync

What Paper's design token system cannot express, how to cover the difference in
the codebase, and how to keep the two from drifting apart.

Companion to `tailwind-v4-theming-with-paper.md`, which covers the token model
itself (theming and responsive sizing).

---

## Coverage map

Paper supports exactly ten token types. Each maps cleanly onto a Tailwind v4
namespace:

| Paper type      | Tailwind namespace | Powers                          |
| --------------- | ------------------ | ------------------------------- |
| `color`         | `--color-*`        | `bg-*`, `text-*`, `border-*`    |
| `fontFamily`    | `--font-*`         | `font-*`                        |
| `fontSize`      | `--text-*`         | `text-*`                        |
| `fontWeight`    | `--font-weight-*`  | `font-bold`, `font-medium`      |
| `letterSpacing` | `--tracking-*`     | `tracking-*`                    |
| `lineHeight`    | `--leading-*`      | `leading-*`                     |
| `spacing`       | `--spacing-*`      | `p-*`, `m-*`, `gap-*`           |
| `radius`        | `--radius-*`       | `rounded-*`                     |
| `breakpoint`    | `--breakpoint-*`   | `sm:`, `md:`, `lg:`             |
| `container`     | `--container-*`    | `max-w-*`, `@sm:` variants      |

Tailwind v4 has more namespaces than that. The rest are the subject of this
document.

## 1. Namespaces Paper cannot store

| Namespace          | Utilities             | Domain            |
| ------------------ | --------------------- | ----------------- |
| `--shadow-*`       | `shadow-md`           | Elevation         |
| `--inset-shadow-*` | `inset-shadow-sm`     | Elevation         |
| `--drop-shadow-*`  | `drop-shadow-lg`      | Elevation         |
| `--text-shadow-*`  | `text-shadow-sm`      | Elevation         |
| `--blur-*`         | `blur-md`, `backdrop-blur-md` | Depth     |
| `--ease-*`         | `ease-out`            | Motion            |
| `--animate-*`      | `animate-spin`        | Motion            |
| `--aspect-*`       | `aspect-video`        | Layout            |
| `--perspective-*`  | `perspective-near`    | 3D                |

**Elevation and motion have no home in Paper.** They get drawn on the canvas as
literal values and then reinvented in code — the exact drift the token system
exists to prevent.

### Strategy: one generated region, everything else owned

The consumer stylesheet has three regions, in this order. Only the middle one is
machine-written, and it is delimited by markers a regenerator can find:

```css
/* Region 1 — palette, owned by the application */
:root { --ground: #F5E9DB; }

/* paper-tokens:generated:start
   Regenerating replaces everything between these two markers.
   contentHash.tokens: <final hash> */
@theme inline {
  --color-ground: var(--ground);
  --font-display: Caprasimo;
  /* ... generated by get_tokens({ format: "tailwind" }) ... */
}
/* paper-tokens:generated:end */

/* Region 3 — codebase-owned, no Paper equivalent, maintained here */
@theme {
  --shadow-raised:  0 1px 2px rgb(36 19 10 / 0.06),
                    0 4px 12px rgb(36 19 10 / 0.08);
  --shadow-overlay: 0 12px 32px rgb(36 19 10 / 0.16);

  --ease-entrance: cubic-bezier(0.16, 1, 0.3, 1);
  --ease-exit:     cubic-bezier(0.4, 0, 1, 1);

  --animate-fade-up: fade-up 0.4s var(--ease-entrance);

  @keyframes fade-up {
    from { opacity: 0; transform: translateY(8px); }
    to   { opacity: 1; transform: none; }
  }
}
```

Two rules that make this survive contact with a team:

- **Derive shadow colors from the palette**, not from neutral black. A shadow
  built on `rgb(0 0 0 / 0.1)` under a warm ground reads as dirt. Tint it with the
  ink color so elevation belongs to the same scene.
- **Regeneration replaces the marked region and nothing else.** Fallback font
  stacks, `--text-*--line-height` / `--text-*--letter-spacing` pairs, namespace
  resets, the derived `--spacing` base, and the motion layer belong to the owned
  regions. Put any of them inside the markers and the next export deletes them.
- **The template is a template.** Copy `assets/paper-tokens.css` into the
  consumer codebase once; the installed skill asset is never the export target.

## 2. Font families ship without a fallback stack

Paper stores the family name and nothing else:

```css
--font-display: Caprasimo;   /* what get_tokens exports */
```

If the face is not loaded in the application, the browser falls back to its
default with no error. The design looks *almost* right and the cause is not
obvious.

Add the stack — and the loading — on the codebase side:

```css
@theme {
  --font-display: "Caprasimo", ui-serif, Georgia, serif;
  --font-body:    "Syne", ui-sans-serif, system-ui, sans-serif;
  --font-accent:  "Meow Script", cursive;
}
```

Paper stores no `@font-face`, no weights-to-load, no `font-display` strategy.
That is application configuration — `next/font`, `@fontsource`, or a manual
`@font-face` block.

> Before styling type in Paper for the first time in a session, call
> `get_font_family_info` to confirm the family and the weights actually exist.
> Using an unavailable weight produces a broken design that screenshots fine.

## 3. Line-height units change inheritance behavior

Tailwind's default `--leading-*` values are **unitless**:

```css
--leading-tight: 1.25;
--leading-normal: 1.5;
```

Paper's guide recommends `px`, and files in practice often use `%`. All three
are valid CSS, but they do not inherit the same way:

| Form            | What inherits                    | Effect on children             |
| --------------- | -------------------------------- | ------------------------------ |
| `1.5` (unitless)| The **ratio**                    | Recomputed per element         |
| `120%`          | The **computed px value**        | Fixed for the whole subtree    |
| `24px`          | The **computed px value**        | Fixed for the whole subtree    |

Set `leading-normal: 120%` on a container with 16px text and every descendant
inherits `19.2px` — including the 40px heading inside it, which then collides
with itself.

**Rule:** use unitless for anything applied to a container or inherited.
Reserve `px` / `%` for a token applied to the same element that sets its own
font size.

Conversion is only arithmetic for two of the six branches. The full table:

| Stored form | Exported | Rule |
| --- | --- | --- |
| `1.2` | `1.2` | Already a ratio; pass through |
| `120%` | `1.2` | Divide by 100 |
| `1.2em` | `1.2` | The `em` multiplier *is* the ratio |
| `24px` | `1.2` **only** with a recorded intended ratio, or an explicitly paired font size (`24px` leading on `20px` text) | Otherwise unresolved |
| `var(--other)` | Resolve the target first, then apply its branch | Unresolved if the target is missing or the alias cycles |
| `calc(...)`, keywords, anything else | — | Unresolved |

```css
/* Paper                 →  Tailwind */
--leading-none:   90%    →  0.9
--leading-tight:  100%   →  1
--leading-normal: 120%   →  1.2
--leading-loose:  180%   →  1.8
--leading-em:     1.2em  →  1.2
--leading-fixed:  24px   →  unresolved without an intended ratio
```

**Unresolved is a reportable outcome, not a failure to hide.** Name the token,
quote its stored value, and say why it could not be converted. A guessed root
font size produces a ratio that is wrong everywhere the real size differs.

An absolute value MAY stay absolute when the token is applied to the same
element that sets its own font size — that is the one case where nothing
inherits it. Record that element scope in the token `description`, otherwise the
next export cannot tell an intentional fixed leading from an unconverted one.

> **Paper cannot store the converted value.** Writing `1.2` to a `lineHeight`
> token normalizes to `120%` on save — verified: writing `2` stored `200%`.
> `%`, `px` and `em` are all preserved, and all three inherit an already-computed
> pixel value; unitless is the only form that inherits a ratio, and the only one
> Paper rejects. There is no workaround inside Paper. The
> conversion is a mandatory export-time step in the codebase, in the same class
> as `clamp()` and the dark-mode palette swap. Record the intended ratio in the
> token `description` so the export step has a source of truth.

## 4. Font size cannot carry its own line height

Tailwind v4 lets a font-size utility bundle a default line height:

```css
@theme {
  --text-lg: 28px;
  --text-lg--line-height: 1.2;
  --text-lg--letter-spacing: -0.01em;
}
```

Now `text-lg` sets size, leading and tracking in one class.

Paper cannot store the pairing in the theme — `fontSize`, `lineHeight` and
`letterSpacing` are three independent token types. Note that `get_jsx` *does*
emit the pairing per element as `text-5xl/none`; the gap is at the theme layer,
where a size utility should carry its own defaults. Reassemble the pairs on the
codebase side after export, in the same block where the export lands. This is
the single highest-value manual step: it turns three classes into one and stops
type from drifting apart across components.

## 5. Custom tokens do not replace the defaults

Already covered for breakpoints in the companion doc — it applies to every
namespace. A file with `--radius-button: 15px` still ships `rounded-xs` through
`rounded-4xl`. A file with `--text-2xs` and `--text-md` still ships the full
default type scale.

The result is a mixed vocabulary where nobody knows which scale is canonical.

Clear the namespace when you intend to own it:

```css
@theme {
  --radius-*: initial;
  --radius-button: 15px;
  --radius-card:   24px;

  --font-weight-*: initial;
  --font-weight-regular:  400;
  --font-weight-semibold: 600;
}
```

Decide per namespace. Owning `--color-*` completely is normal; owning
`--spacing-*` completely is usually a mistake, since v4 derives every step from
a single `--spacing` base.

## 6. Renaming a token breaks classes silently

`set_tokens` with `newName` rewrites the variable. It does not — and cannot —
rewrite the utility classes built from it:

```
--color-accent  →  --color-brand
```

Every `bg-accent`, `text-accent` and `border-accent` in the codebase is now a
class Tailwind does not generate. No build error. No type error. The element
simply loses its color.

**The obvious protocol is broken.** Creating the new token as
`--color-brand: var(--color-accent)` and then deleting `--color-accent` leaves
the new token pointing at a name that no longer exists. The custom property
resolves to empty and the element falls back to inherited ink — reproduced in
`tests/browser.test.mjs` (`alias deletion`). A zero-hit search on utility
classes does not catch it, because the dangling reference is token-to-token.

**Migration protocol — direction matters:**

1. Create the new token with the **canonical value**, not a reference to the old
   name: `--color-brand: #B45844`.
2. Point the old name at the new one for compatibility:
   `--color-accent: var(--color-brand)`. Both classes now render, and the value
   lives in exactly one place.
3. Migrate consumers: Paper nodes, code usages, and **other tokens** that
   reference the old name.
4. Verify all three consumer kinds. A token-to-token reference is the one a
   `rg` over `src/` will miss.
5. Remove the compatibility alias with `set_tokens`, sending each entry in the
   `tokens` array with its `name`.
6. Read back and confirm the new token still resolves to the canonical value.

**Rollback data:** before step 5, record the old name and the canonical value it
resolved to. Restoring is then re-creating `--color-accent: #B45844`; without
that record, the prior mapping is gone.

Never rename in one step. Keep ambiguous or runtime-assembled consumers on the
compatibility alias — an unused-looking token may be referenced from a class
name built at runtime, which no search will find. Prefer aliasing over deleting
when in doubt.

## 7. Drift detection with `contentHash`

`get_basic_info` returns a hash of the token set:

```json
"contentHash": { "tokens": "068c423f" }
```

This is the mechanism that closes the loop — but only if the hash you store is
the one that describes the tokens you exported.

**Capture it last, not first.** A hash read at the start of the session, before
`create_tokens` ran, describes the design file as it was *before* your work.
Writing it beside the new CSS records the wrong revision and CI will report
"in sync" against a design state that no longer exists.

The sequence:

1. Immediately before `get_tokens`, read `contentHash.tokens` from the file.
2. Export.
3. Read `contentHash.tokens` from **the same file** again.
4. Equal → record it beside the generated CSS. Different → someone changed the
   file mid-export; re-export or stop. Unreadable → report incomplete evidence
   and record nothing.

```
styles/
  paper-tokens.css        # generated region + owned regions
  paper-tokens.hash       # the final contentHash, bound to one file id
```

Store the file id alongside the hash. A hash without its source file is not a
drift check, it is a string.

```bash
# ILLUSTRATIVE PSEUDOCODE — `paper-token-hash` does not exist.
# A consumer supplies its own adapter that calls get_basic_info over live MCP
# and prints contentHash.tokens for the recorded file id.
current=$(cat styles/paper-tokens.hash)
latest=$(paper-token-hash "$PAPER_FILE_ID")

if [ -z "$latest" ]; then
  echo "Paper unreachable — drift unknown, not clean."
  exit 2
fi
if [ "$current" != "$latest" ]; then
  echo "Design tokens changed in Paper. Re-export and commit."
  exit 1
fi
```

Note the third state. An unreachable design file is **unknown**, never a pass;
a check that exits 0 when it could not reach Paper is worse than no check.

Without this, drift is discovered visually — someone notices a color is off,
weeks later. With it, the design file and the codebase disagree loudly, once,
at the moment it happens.

## Coverage checklist

- [ ] Elevation and motion tokens live in a clearly marked codebase-owned block.
- [ ] Shadow colors derived from the palette, not neutral black.
- [ ] Regeneration replaces only the delimited generated region.
- [ ] The template was copied into the consumer; the skill asset is untouched.
- [ ] Every `--font-*` token has a fallback stack.
- [ ] Font loading configured in the application (`@font-face` / `next/font`).
- [ ] Inherited `--leading-*` unitless; unresolved values reported, not guessed.
- [ ] `--text-*--line-height` pairs reassembled in an owned region after export.
- [ ] Each namespace either fully default or cleared with `initial`.
- [ ] Renames give the new token the canonical value, alias the *old* name to it,
      then remove the alias — and rollback data is recorded first.
- [ ] Final `contentHash.tokens` stored with its file id; unreachable ≠ clean.
